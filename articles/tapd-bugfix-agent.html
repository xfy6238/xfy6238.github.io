AGENT 工程 · 缺陷自治

缺陷自治修复 Agent：拉取→分类→修复→验证→两段式回写

阅读约 9 分钟 · 四件套形态 · 两段式回写 · 护栏与失败预算
结论先行

能自动修的 bug，应该以最少人工干预闭环：拉取 → 分类 → 修复 → 跑测试 → 人工批准 → 回写。关键只有三处——写操作永远两段式、护栏只拒绝不回滚、失败预算写死。

背景：修 bug 的时间都去哪了

迭代里永远有一类 bug：必现、定位清晰、改动小（空指针判空、越界、文案错位、参数传错）。它们单个修起来都不到半小时，但流程很碎：看单、拉分支、复现、改、跑测试、更新单子、等验证。碎时间加起来，一个迭代能吃掉几个人日。

这类活恰好适合本地 Agent：它直接读代码仓、改代码、跑测试?n飞全程不需要人。而“回写单子”这一步必须卡人工——让 Agent 自己关单，等于把质量 gate 交了出去。所以形态很明确：读和修自治，写要批准。

注意这东西只能是本地执行型：能力依赖本地代码仓 + 本地跑测试，做成网页版要换架构，还丢掉核心优势。

1四件套：它到底由什么组成

这不是一个单一程序，而是一套分层件，每层职责单一：

件 职责 关键点
修复 skill（Agent 本体） 定义角色与工作流：拉取→分类→修复→测试→回写 分类决策表写死，不靠临场发挥
MCP 工具层 4 个工具：查列表 / 查详情 / 生成修改提案 / 提交更新 allowlist、状态机、幂等键、审批签名
护栏扩展 拦截危险路径写入，记审计日志 只拒绝不回滚，防丢用户改动
查询 skill + 改进者 skill 查单汇总；拿人类反馈生成对本体的最小修改提案 改进也要人确认才生效
分层的意义：换缺陷平台只换 MCP 层；换团队规范只改护栏黑名单；工作流本身不动。

2两段式回写：写操作的设计

所有对外写动作拆成两段，中间必须经过人：

tapd_get_bugs（按优先级/模块拉取）
  → 决策表分类 [可自动修] / [转人工]
  → get_detail 深挖 → 定位根因 → 改代码（受护栏约束）
  → 跑测试（失败最多再修 3 次）
  → prepare_update 生成提案预览（含 diff + 测试结果）
  → ★ 人工批准（approve，签发 approval_token）
  → commit_update（凭 token，一次有效，幂等）

三处细节：token 一次有效，用过即废，防重放；幂等键，同一提案重复提交只生效一次，崩溃重启也不怕；allowlist fail-closed，状态不在白名单里默认拒绝，而不是默认放行。

3护栏：只拒绝，不回滚

护栏拦截三类写入：敏感目录（如鉴权、支付、配置、密钥文件）、黑名单路径、越权操作。策略上刻意选了“只拒绝不自动回滚”：

  • 自动回滚可能丢掉用户正在写的改动，误伤比漏放更贵。
  • 拒绝时给出明确原因 + 审计日志，人在回放时能看清边界。
  • 黑名单放配置文件里，换团队只改配置，不动代码。

凭据同样分级：真实 token 文件权限 0600，分发只带 .env.example，真实 .env 永不进仓库；环境变量优先于文件，文档只写一种口径，避免配错地方。

4分类决策表与失败预算

Agent 最危险的不是修错，而是不知道停。两道闸：

  • 分类闸：黑名单命中 → 直接转人工；资金/权限风险 → 转人工；类型不在可自动修清单 → 转人工。默认面要窄，跑顺了再放宽。
  • 失败预算：单个 bug 修 3 次不过就停；连续 2 个 bug 失败整会话停并上报；单会话最多处理 5 个。预算写死在 skill 里，不是“建议”。

5大小模型分工：别让小模型干它干不了的

实测结论：小模型能干分类打标和摘要压缩，干不了多步工具调用和稳定结构化输出。所以分工是：小模型只做初筛（打标签、压摘要），大模型做修复和定稿。配套三件套：只让小模型输出枚举标签或纯文本（不准要 JSON）、低温度+模板约束、失败重试一次后转大模型兜底。先小批量评测，行了再全量。

6落地建议

  • 分发用包机制（skills + extensions 约定目录自动发现，一条安装命令），团队内项目级声明自动安装。
  • 先只跑前半段验证：真实拉取 → 分类 → 生成提案（不提交），确认分类与提案质量后再开提交。
  • 攒真实反馈：按“日期｜单号｜现象｜误判｜期望”记，攒够一批再让改进者 skill 提最小修改。
